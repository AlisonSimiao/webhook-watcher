# Eventos são snapshots entregues pelo menos uma vez

Cada Evento carrega o estado completo e atual do Recurso (event-carried state transfer), lido no MariaDB no momento do enriquecimento — não o estado do instante exato do binlog, nem um evento de domínio nomeado ("PedidoFaturado"). A entrega é pelo menos uma vez: um restart reprocessa alguns segundos de binlog e o dedup do asynq só vale enquanto a task ainda está no Redis, e um retry pode entregar um snapshot depois de um mais novo do mesmo Recurso. Quem consome compara `dataEvento` (instante da leitura do estado, ISO-8601 UTC com milissegundos) e descarta o que for mais antigo que o último recebido — uma entrega duplicada é inofensiva, pois carrega o mesmo estado e a mesma data. A ordem por shard no consumer HTTP é melhor esforço, não garantia: bloquear o shard em falha foi rejeitado porque atrasaria todos os Recursos do shard e o fan-out assíncrono do srp-hub-api embaralha a ordem de qualquer forma. Exatamente uma vez não é viável com binlog + Redis + HTTP, e eventos de domínio exigiriam inferir intenção de negócio a partir de diffs de linha.

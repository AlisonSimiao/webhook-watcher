# AGENTS.md

Go 1.26 binary (`module webhook-watcher`) that tails a MariaDB binlog and turns row changes into webhook events, delivered via a pluggable event-driven consumer architecture. Packages: `main` (`.go` files at repo root), `config`, `producer`, `tables` (+ `tables/pedido`), `pkg/queue`, and `consumer/webhook`.

## Commands

- Build/vet/test: `go build ./...`, `go vet ./...`, `go test ./...` — all pass. Tests cover `main` (binlog_test.go: `decideStartPosition`), `config` (migration, position persistence, failed_events, failed_deliveries), `producer` (strategy emit/enqueue, generateEventID), `pkg/queue` (MemoryQueue, FanoutQueue, ShardedQueue), `consumer/webhook` (Delivery via httptest, no real network/DB needed). No lint/CI.
- **Do not** build with `go build -o webhook-watcher main.go`. That compiles only `main.go` and fails with `undefined: newBinlogWatcher`, because `binlog.go`, `server_cmd.go`, `failed_events_cmd.go`, `failed_deliveries_cmd.go`, `consumer_cmd.go`, and `logging.go` are also `package main`. Build with `.` instead (the Dockerfile does this; it also needs `COPY . .` before building — it already has it).
- Run `gofmt -w` before committing edits to `config/config.go`.
- Subcommands that return before `initQueue()` (**don't** need Redis; `failed-events`/`failed-deliveries` need the SQLite DB):
  - `go run . server add|list|update|remove` — manage `binlog_servers` instead of editing SQLite by hand (see README for flags; `replica_id`/`server_id` are UNIQUE).
  - `go run . failed-events list|remove` — inspect/delete rows from the `failed_events` dead-letter table (producer-side: enqueue failures).
  - `go run . failed-deliveries list|remove` — inspect/delete rows from the `failed_deliveries` dead-letter table (consumer-side: failures repassing an event to `srp-hub-api` after asynq exhausts retries).
  - `go run . consumer http` — **does** need `REDIS_ADDR` + `SRP_HUB_API_BASE_URL` + `SRP_HUB_API_TOKEN` + `HTTP_CONSUMER_SHARDS`. Starts the HTTP webhook consumer (see Architecture below); long-running, not a one-shot subcommand.

## Runtime requirements

- DB credentials live in a local **SQLite** file (`servers.db`, configurable via `SQLITE_PATH`), table `binlog_servers`, loaded via `config.LoadServersFromDB()` (only `is_active = 1`). On first run, if the table is empty, `main.go` seeds a default server from `config.DefaultServerConfig()`. `main.go` calls `godotenv.Load()` first, so the seed (and only the seed) reads env vars from `.env` (`SERVER_ID`, `REPLICA_ID`, `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_FLAVOR`) with development defaults (localhost:3306, root/kodejifr, 'DB01'). `.env` and `servers.db` are gitignored; `.env.example` documents the vars. Only way to run: point at a MariaDB reachable from this host.
- **Redis is required** to run the watcher (`REDIS_ADDR`; `main.go`'s `initQueue()` fails fast if missing) and the HTTP consumer. Local infra via `docker compose up -d` maps **5000:6379**, so `REDIS_ADDR=localhost:5000`; asynqmon on localhost:8080.
- Needs a user with replication privileges and `SHOW MASTER STATUS` access; server must have binlog enabled with `binlog_row_image=FULL` if old-row data matters.
- `binlog_servers.replica_id` is `UNIQUE` — it is the replication replica ID; two watchers with the same replica_id against the same source get rejected.
- **Resume-on-restart is per server**: `binlog_servers.binlog_file`/`binlog_pos` store the last read position (columns added by an additive `ALTER TABLE` migration for old DBs). `decideStartPosition` (binlog.go) resumes from the saved position; only a fresh server (empty position) runs `SHOW MASTER STATUS`. `persistPosition` writes on binlog rotation, every ~5s of advance, and on shutdown/SIGINT/SIGTERM.
- **The HTTP consumer needs no database of its own to resolve destinations** — it repasses each event to `srp-hub-api`'s `/interno/hooks/<tipo>` route (`SRP_HUB_API_BASE_URL`), which does the `clientes_hooks`/`cliente` lookup and client fan-out itself. `SRP_HUB_API_TOKEN` is the raw value sent in the `Authorization` header (no `Bearer` prefix) — it must match a `cliente_hub_autenticacao` row for `tenant = 'srp'` on `srp-hub-api`'s side; there is no dev default, it has to be requested from whoever administers that table. The consumer is stateless across restarts: nothing to resume, no cache to warm.
- **`HTTP_CONSUMER_SHARDS` (env var, default 16) must match between the producer (`go run .`) and the consumer (`go run . consumer http`)** — it's a shared tuning knob, not a connection, so it stays an env var rather than SQLite. A mismatch routes some events to a shard nobody is listening to — they sit in Redis with no error. See `httpShardCount()` in `server_cmd.go`.
- Comments and log output are in Portuguese — keep that style.

## Architecture

- Flow: `main.go` → `config.InitDB()` + `config.LoadServersFromDB()` → **one goroutine per server** → `BinlogWatcher.Start()` (`binlog.go`) → per-event `Producer.HandleEvent()` (`producer/`). `main.go` waits on a `sync.WaitGroup`; a failing server (or panic, which is recovered) logs its error without killing the others.
- Logs are structured JSON via `slog` (JSON handler on stdout) for CloudWatch. `BinlogWatcher` carries a `server_id` attr (no `[DB01]` prefix anymore); binlog events carry `binlog_file`/`binlog_pos`; the producer logs processed events under an `evento` attr. `main.go` installs `dropMessageHandler` (logging.go) to filter the `create BinlogSyncer` line that go-mysql emits with a non-serializable config.
- `binlog.go` listens in a loop with a 2s context timeout; `context.DeadlineExceeded` is expected and just `continue`s. It handles `RotateEvent` (updates `pos.Name`/`pos.Pos` on rollover, persists, `continue`s). `HandleEvent` receives the **pre-mutation** position — `pos.Pos = ev.Header.LogPos` advances only afterward; don't reorder.
- `producer/` dispatches via **Strategy + Registry**: `Producer` (producer.go) holds `map[replication.EventType]EventStrategy`; `HandleEvent` routes each event type to its strategy. `UpdateRowsStrategy` (update.go) handles UPDATE v1/v2 + MariaDB compressed; it embeds `RowsStrategy` (rows.go), which provides the shared ROWS logic (`eachRow` iterates rows with stride/offset per action; `rowResourceID` extracts the resource ID; `emit` logs and enqueues). **Only tables with a registered `TableProcessor` produce events** — others are logged at Debug. Registering a new event type = add a map entry + new strategy file.
- UPDATE rows arrive as old/new pairs — stride 2, new row at `Rows[i+1]`; INSERT/DELETE would use stride 1, offset 0. `rowResourceID` accepts `int32` or `uint32` in column 0 (ids are `int unsigned` in the source DB; non-integer columns are logged and skipped); `Table.Schema` = tenant, `Table.Table` = table. Enrichment (MariaDB queries in the `TableProcessor`) happens in the producer, before enqueue.
- Event ID = `evt_` + SHA-256 (first 16 bytes hex) over `binlogFile:logPos:rowIndex:tenant:table:resourceID`. Known sharp edge: `generateEventID` relies on `rowIndex` being unique per event to guarantee distinct IDs for same-resource rows.
- **Dead-letter, not retry (producer side)**: in `emit`, enqueue errors that are not duplicates (`queue.IsDuplicate`) are saved to the `failed_events` table in `servers.db` via `config.SaveFailedEvent` — no automatic retry or reprocessing. Inspect with `go run . failed-events list`; the full payload is only visible via direct SQL (`sqlite3 servers.db "SELECT payload FROM failed_events WHERE id = N"`).
- `pkg/queue/` is the queue **port** (Ports & Adapters): `Enqueuer` (Enqueue/Close), envelope `Event` (ID/tenant/table/action/timestamp/**resourceID**/payload), and `MemoryQueue` for tests. `RedisQueue` (redis.go) is the Redis adapter via **asynq**, parametrized by queue name, using `Event.ID` as the task `TaskID` (idempotent per queue — `ErrDuplicate`/`IsDuplicate`); `RedisWorker` (redis_consumer.go) is the consumer side, also parametrized by queue name (asynq server + typed `Handler`; retry/backoff/dead-letter handled by asynq).
- **Event-driven fan-out + sharding** (`pkg/queue/fanout.go`, `pkg/queue/sharded.go`): asynq is a competing-consumers work queue — two *different* consumer types reading the same queue would each only get some of the events, not a copy each. `FanoutQueue` solves that by publishing the same `Event` to one named queue **per consumer type** (`queue.QueueNameHTTP` = `"webhook-events.http"`). Adding a new type is: a `QueueNameX` constant next to `QueueNameHTTP` in `queue.go`, a `consumer/<type>/` package exposing a `Handle(ctx, *queue.Event) error` (satisfies `queue.Handler`), one more target line in `main.go:initQueue()`, and a new `case` in `consumer_cmd.go`'s `runConsumerCommand` — nothing in `producer/`, `binlog.go`, or `queue.Event`/`Enqueuer`/`Handler` needs to change, since the producer only ever sees the single opaque `Enqueuer` it was given. Within the HTTP type, `ShardedQueue` further routes (not replicates) each event to exactly one of N sub-queues (`queue.QueueNameHTTPShard(i)`) by a stable hash (`hash/fnv`, **not** `hash/maphash`) of `tenant:table:resourceID` — same resource always lands on the same shard, and each shard is consumed by a worker with `Concurrency: 1`, which is what actually preserves delivery order per resource (the hashing alone only guarantees *co-location*, not order — order comes from single-threaded consumption within a shard). `N` (`HTTP_CONSUMER_SHARDS`) must match between producer and consumer (see Runtime requirements).
- `initQueue()` in `main.go` builds `FanoutQueue{ ShardedQueue{ RedisQueue × N shards } }` from `REDIS_ADDR` + `HTTP_CONSUMER_SHARDS`.
- **`consumer/webhook/`** — the HTTP webhook consumer (wired up in `consumer_cmd.go`, `go run . consumer http`, one goroutine per shard, each its own `RedisWorker` at `Concurrency: 1`). `Delivery.Handle` (deliver.go) is the `queue.Handler`: maps `Event.Table` to a `tipo` segment via `tableToTipo` (currently just `"pedidos": "pedidos"` — confirmed identical to the table name, no singular/plural translation, against `srp-hub-api`'s own `src/config/constants.js`: `WEBHOOK.TIPO = { PEDIDO: 'pedidos', CLIENTE: 'clientes' }`; a table absent from the map is a silent no-op, not an error), then `POST`s `Event.Payload` **as-is** (already `{tipoModificacao, recurso}`, no re-enveloping) to `<SRP_HUB_API_BASE_URL>/interno/hooks/<tipo>`, with `Authorization: <SRP_HUB_API_TOKEN>` (raw, no `Bearer`) and `tenant: <Event.Tenant>` headers. Any failure (transport or non-2xx) returns an error, triggering asynq's own retry/backoff; on the *last* attempt (`asynq.GetRetryCount`/`GetMaxRetry` from the handler's `ctx`), the failure is also persisted to `failed_deliveries` (SQLite) — dead-letter parity with the producer side, inspectable via `go run . failed-deliveries list`.
- **This consumer does not resolve per-client destination URLs itself, and does not read `clientes_hooks`/`cliente` at all** — that whole lookup (and the client-facing fan-out) is `srp-hub-api`'s job on the other end of `/interno/hooks/<tipo>`. This was a deliberate architecture change (see "Current state" below) from an earlier version that queried `clientes_hooks`/`cliente` directly.
- **Ordering caveat past the handoff to `srp-hub-api`**: that route responds to the caller *before* its own fan-out to the client's webhook URL finishes (`hook.controller.js` sends the response, then continues the delivery asynchronously). This consumer's per-shard `Concurrency: 1` still guarantees the order in which **we** call `srp-hub-api` for a given resource, but not the order those calls actually land at the end client — two of `srp-hub-api`'s own in-flight deliveries for the same resource can race independently of the order we invoked them in. This is a pre-existing characteristic of that route, not something this consumer introduces.

## Current state / next steps

- **Built**: full fan-out (`FanoutQueue`) + sharded (`ShardedQueue`) event-driven queue architecture, and an HTTP consumer (`consumer/webhook/`, `go run . consumer http`) that repasses events to `srp-hub-api`'s `/interno/hooks/<tipo>` route, with its own dead-letter table (`failed_deliveries`).
- **Architecture pivot, mid-project**: the consumer originally resolved destinations itself (querying `clientes_hooks`/`cliente` directly on a dedicated hub MariaDB connection, with an in-memory cache refreshed every 5 minutes, config in a `hub_config` SQLite table managed by a `go run . hub set|show|query` subcommand). That was replaced by routing through `srp-hub-api`'s existing `/interno/hooks/<tipo>` endpoint instead, once it was confirmed that endpoint already does the same `clientes_hooks`/`cliente` resolution and already emits the exact payload shape (`{tipoModificacao, recurso}`) this consumer's `Event.Payload` already carries — removing this repo's dependency on a schema/table it doesn't own, at the cost of the ordering caveat above. If you find references to `hub_config`, `HookCache`, or `go run . hub` in old context (a stale plan doc, old chat history), they describe the earlier, now-replaced design.
- **Duplicate-delivery risk — resolved by plan, not by code**: `/interno/hooks/<tipo>` is currently triggered by an external "SRP legacy" system (not `hub-events` — that was an earlier, incorrect assumption; `hub-events` calls a different, unrelated route, `/interno/queue/hooks`). This project is still in development; per the user, that legacy system will stop calling `/interno/hooks/<tipo>` once this project reaches production, so the two won't be triggering the same resource changes concurrently. Nothing to implement here — just don't run this consumer against production data while the legacy system might still be active for the same resources.
- **Still open — external, not resolvable from this repo alone**: `SRP_HUB_API_TOKEN` requires a **new** `cliente_hub_autenticacao` row on `srp-hub-api`'s database — `tenant` must be `'srp'` (the auth middleware there requires exactly that value to grant access to `/interno/hooks/*`, it's not a free choice), but with its **own token**, distinct from the legacy system's, and a `rate_limit` sized for this consumer's volume (rate limiting there is keyed by the `Authorization` header value, not the tenant). Someone with access to that table has to provision it — no dev default exists.
- SSE and notification consumer types are not implemented — the extension seam is deliberately left as a comment in `main.go:initQueue()` and documented with a concrete step-by-step (new `QueueNameX` + new `consumer/<type>` package + one line in `initQueue` + one `case` in `consumer_cmd.go`).
- Resource coverage: only `pedidos`/`UPDATE` produces events today (`tableToTipo` only maps that one); `srp-hub-api`'s hook route also validates `clientes` (create/update/delete) and, for `pedidos`, only allows `tipoModificacao` `C`/`M` (no `D`) — relevant once INSERT/DELETE strategies (reuse `RowsStrategy` with their own stride) or a `clientes` `TableProcessor` are added.

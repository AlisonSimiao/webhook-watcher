# AGENTS.md

Go 1.26 binary (`module webhook-watcher`) that tails a MariaDB binlog and turns row changes into webhook events, delivered via a pluggable event-driven consumer architecture. Packages: `main` (`.go` files at repo root), `config`, `producer`, `tables` (+ `tables/pedido`), `pkg/queue`, and `consumer/webhook`.

## Commands

- Build/vet/test: `go build ./...`, `go vet ./...`, `go test ./...` — all pass. Tests cover `main` (binlog_test.go: `decideStartPosition`; hub_query_test.go: `checkHookColumns`), `config` (migration, position persistence, failed_events, failed_deliveries, hub_config), `producer` (strategy emit/enqueue, generateEventID), `pkg/queue` (MemoryQueue, FanoutQueue, ShardedQueue), `consumer/webhook` (HookCache lookup, Delivery via httptest). No lint/CI.
- **Do not** build with `go build -o webhook-watcher main.go`. That compiles only `main.go` and fails with `undefined: newBinlogWatcher`, because `binlog.go`, `server_cmd.go`, `failed_events_cmd.go`, `failed_deliveries_cmd.go`, `hub_cmd.go`, `consumer_cmd.go`, and `logging.go` are also `package main`. Build with `.` instead (the Dockerfile does this; it also needs `COPY . .` before building — it already has it).
- Run `gofmt -w` before committing edits to `config/config.go`.
- Subcommands that return before `initQueue()` (**don't** need Redis; `failed-events`/`failed-deliveries`/`hub` need the SQLite DB, `hub query` also dials the hub MariaDB):
  - `go run . server add|list|update|remove` — manage `binlog_servers` instead of editing SQLite by hand (see README for flags; `replica_id`/`server_id` are UNIQUE).
  - `go run . failed-events list|remove` — inspect/delete rows from the `failed_events` dead-letter table (producer-side: enqueue failures).
  - `go run . failed-deliveries list|remove` — inspect/delete rows from the `failed_deliveries` dead-letter table (consumer-side: HTTP delivery failures after asynq exhausts retries).
  - `go run . hub set|show|query` — configure/inspect the `hub_config` row (MariaDB connection + the resolution query for webhook destinations); `hub query` runs the configured query for real and validates its column shape (`tenant`/`tipo`/`url`) before you trust it in `consumer http`.
  - `go run . consumer http` — **does** need `REDIS_ADDR` + `hub_config` already set (`go run . hub set`) + `HTTP_CONSUMER_SHARDS`. Starts the HTTP webhook consumer (see Architecture below); long-running, not a one-shot subcommand.

## Runtime requirements

- DB credentials live in a local **SQLite** file (`servers.db`, configurable via `SQLITE_PATH`), table `binlog_servers`, loaded via `config.LoadServersFromDB()` (only `is_active = 1`). On first run, if the table is empty, `main.go` seeds a default server from `config.DefaultServerConfig()`. `main.go` calls `godotenv.Load()` first, so the seed (and only the seed) reads env vars from `.env` (`SERVER_ID`, `REPLICA_ID`, `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_FLAVOR`) with development defaults (localhost:3306, root/kodejifr, 'DB01'). `.env` and `servers.db` are gitignored; `.env.example` documents the vars. Only way to run: point at a MariaDB reachable from this host.
- **Redis is required** to run the watcher (`REDIS_ADDR`; `main.go`'s `initQueue()` fails fast if missing) and the HTTP consumer. Local infra via `docker compose up -d` maps **5000:6379**, so `REDIS_ADDR=localhost:5000`; asynqmon on localhost:8080.
- Needs a user with replication privileges and `SHOW MASTER STATUS` access; server must have binlog enabled with `binlog_row_image=FULL` if old-row data matters.
- `binlog_servers.replica_id` is `UNIQUE` — it is the replication replica ID; two watchers with the same replica_id against the same source get rejected.
- **Resume-on-restart is per server**: `binlog_servers.binlog_file`/`binlog_pos` store the last read position (columns added by an additive `ALTER TABLE` migration for old DBs). `decideStartPosition` (binlog.go) resumes from the saved position; only a fresh server (empty position) runs `SHOW MASTER STATUS`. `persistPosition` writes on binlog rotation, every ~5s of advance, and on shutdown/SIGINT/SIGTERM.
- **The HTTP consumer needs its own MariaDB connection**, to a fixed `hub_<ambiente>` schema (destinations live there, not in any tenant schema) — configured via `hub_config` (SQLite, `go run . hub set`), not env vars, matching the `binlog_servers` pattern. The consumer is stateless across restarts: no offset to resume, just an in-memory cache rebuilt on boot and refreshed every 5 minutes.
- **`HTTP_CONSUMER_SHARDS` (env var, default 16) must match between the producer (`go run .`) and the consumer (`go run . consumer http`)** — it's the one config value not read from `servers.db`, because it's a shared tuning knob rather than a connection. A mismatch routes some events to a shard nobody is listening to — they sit in Redis with no error. See `httpShardCount()` in `server_cmd.go`.
- Comments and log output are in Portuguese — keep that style.

## Architecture

- Flow: `main.go` → `config.InitDB()` + `config.LoadServersFromDB()` → **one goroutine per server** → `BinlogWatcher.Start()` (`binlog.go`) → per-event `Producer.HandleEvent()` (`producer/`). `main.go` waits on a `sync.WaitGroup`; a failing server (or panic, which is recovered) logs its error without killing the others.
- Logs are structured JSON via `slog` (JSON handler on stdout) for CloudWatch. `BinlogWatcher` carries a `server_id` attr (no `[DB01]` prefix anymore); binlog events carry `binlog_file`/`binlog_pos`; the producer logs processed events under an `evento` attr. `main.go` installs `dropMessageHandler` (logging.go) to filter the `create BinlogSyncer` line that go-mysql emits with a non-serializable config.
- `binlog.go` listens in a loop with a 2s context timeout; `context.DeadlineExceeded` is expected and just `continue`s. It handles `RotateEvent` (updates `pos.Name`/`pos.Pos` on rollover, persists, `continue`s). `HandleEvent` receives the **pre-mutation** position — `pos.Pos = ev.Header.LogPos` advances only afterward; don't reorder.
- `producer/` dispatches via **Strategy + Registry**: `Producer` (producer.go) holds `map[replication.EventType]EventStrategy`; `HandleEvent` routes each event type to its strategy. `UpdateRowsStrategy` (update.go) handles UPDATE v1/v2 + MariaDB compressed; it embeds `RowsStrategy` (rows.go), which provides the shared ROWS logic (`eachRow` iterates rows with stride/offset per action; `rowResourceID` extracts the resource ID; `emit` logs and enqueues). **Only tables with a registered `TableProcessor` produce events** — others are logged at Debug. Registering a new event type = add a map entry + new strategy file.
- UPDATE rows arrive as old/new pairs — stride 2, new row at `Rows[i+1]`; INSERT/DELETE would use stride 1, offset 0. `rowResourceID` accepts `int32` or `uint32` in column 0 (ids are `int unsigned` in the source DB; non-integer columns are logged and skipped); `Table.Schema` = tenant, `Table.Table` = table. Enrichment (MariaDB queries in the `TableProcessor`) happens in the producer, before enqueue.
- Event ID = `evt_` + SHA-256 (first 16 bytes hex) over `binlogFile:logPos:rowIndex:tenant:table:resourceID`. Known sharp edge: `generateEventID` relies on `rowIndex` being unique per event to guarantee distinct IDs for same-resource rows.
- **Dead-letter, not retry (producer side)**: in `emit`, enqueue errors that are not duplicates (`queue.IsDuplicate`) are saved to the `failed_events` table in `servers.db` via `config.SaveFailedEvent` — no automatic retry or reprocessing. Inspect with `go run . failed-events list`; the full payload is only visible via direct SQL (`sqlite3 servers.db "SELECT payload FROM failed_events WHERE id = N"`).
- `pkg/queue/` is the queue **port** (Ports & Adapters): `Enqueuer` (Enqueue/Close), envelope `Event` (ID/tenant/table/action/timestamp/**resourceID**/payload), and `MemoryQueue` for tests. `RedisQueue` (redis.go) is the Redis adapter via **asynq**, parametrized by queue name, using `Event.ID` as the task `TaskID` (idempotent per queue — `ErrDuplicate`/`IsDuplicate`); `RedisWorker` (redis_consumer.go) is the consumer side, also parametrized by queue name (asynq server + typed `Handler`; retry/backoff/dead-letter handled by asynq).
- **Event-driven fan-out + sharding** (`pkg/queue/fanout.go`, `pkg/queue/sharded.go`): asynq is a competing-consumers work queue — two *different* consumer types reading the same queue would each only get some of the events, not a copy each. `FanoutQueue` solves that by publishing the same `Event` to one named queue **per consumer type** (`queue.QueueNameHTTP` = `"webhook-events.http"`). Adding a new type is: a `QueueNameX` constant next to `QueueNameHTTP` in `queue.go`, a `consumer/<type>/` package exposing a `Handle(ctx, *queue.Event) error` (satisfies `queue.Handler`), one more target line in `main.go:initQueue()`, and a new `case` in `consumer_cmd.go`'s `runConsumerCommand` — nothing in `producer/`, `binlog.go`, or `queue.Event`/`Enqueuer`/`Handler` needs to change, since the producer only ever sees the single opaque `Enqueuer` it was given. Within the HTTP type, `ShardedQueue` further routes (not replicates) each event to exactly one of N sub-queues (`queue.QueueNameHTTPShard(i)`) by a stable hash (`hash/fnv`, **not** `hash/maphash`) of `tenant:table:resourceID` — same resource always lands on the same shard, and each shard is consumed by a worker with `Concurrency: 1`, which is what actually preserves delivery order per resource (the hashing alone only guarantees *co-location*, not order — order comes from single-threaded consumption within a shard). `N` (`HTTP_CONSUMER_SHARDS`) must match between producer and consumer (see Runtime requirements).
- `initQueue()` in `main.go` builds `FanoutQueue{ ShardedQueue{ RedisQueue × N shards } }` from `REDIS_ADDR` + `HTTP_CONSUMER_SHARDS`.
- **`consumer/webhook/`** — the HTTP webhook consumer (wired up in `consumer_cmd.go`, `go run . consumer http`, one goroutine per shard, each its own `RedisWorker` at `Concurrency: 1`): `HookCache` (cache.go) keeps an in-memory `map[tenant+tipo][]url`, refreshed every 5 minutes (`StartRefreshLoop`) by re-running the query stored in `hub_config.hook_query` (SQLite) against the hub MariaDB — the query itself is operator-editable at runtime via `go run . hub set -query`, no rebuild/restart needed, because the external `clientes_hooks`/`cliente` schema isn't owned by this repo. `Lookup(tenant, table)` maps `Event.Table` to `clientes_hooks.tipo` via an explicit `tableToTipo` map (`cache.go`) — confirmed against `srp-hub-api`'s own source (`src/config/constants.js`: `WEBHOOK.TIPO = { PEDIDO: 'pedidos', CLIENTE: 'clientes' }`, the system that owns this table today) that `tipo` is **identical** to the table name (plural), no singular/plural translation exists; the map is kept anyway as an explicit allowlist (a table absent from it never produces a lookup, even with a `TableProcessor`). `Delivery.Handle` (deliver.go) is the `queue.Handler`: POSTs the full `queue.Event` envelope as JSON to every resolved URL (no destinations = silent no-op, not an error); any failure (transport or non-2xx) returns an error, triggering asynq's own retry/backoff; on the *last* attempt (`asynq.GetRetryCount`/`GetMaxRetry` from the handler's `ctx`), each failed URL is also persisted to `failed_deliveries` (SQLite) — dead-letter parity with the producer side, inspectable via `go run . failed-deliveries list`.
- **Destination resolution — verified against the real dev schema, one initial assumption was wrong**: `clientes_hooks.id_cliente_hub`'s FK targets `cliente.id` (confirmed via `information_schema.KEY_COLUMN_USAGE` on the local `hub_development` MariaDB), **not** a `cliente_hub` table as the column name suggests — `cliente_hub` exists but isn't part of this join (its `acesso`/`url_base` columns are unused; `acesso` is probably a destination auth token, but its format was never confirmed, so no auth/signing is implemented on outbound requests — open follow-up). `config.DefaultHookQuery` is the verified, working join: `clientes_hooks JOIN cliente ON cliente.id = clientes_hooks.id_cliente_hub`, filtered on `deleted_at IS NULL AND status = 1`.

## Current state / next steps

- **Built**: full fan-out (`FanoutQueue`) + sharded (`ShardedQueue`) event-driven queue architecture, and a complete HTTP webhook consumer (`consumer/webhook/`, `go run . consumer http`) with 5-minute-refreshed destination cache, order-preserving delivery per resource, and its own dead-letter table (`failed_deliveries`). Hub connection + destination-resolution query both live in SQLite (`hub_config`), managed by `go run . hub set|show|query` — matching the `binlog_servers` pattern rather than introducing env vars for a database connection.
- **Still open**: SSE and notification consumer types are not implemented — the extension seam is deliberately left as a comment in `main.go:initQueue()` and documented with a concrete step-by-step (new `QueueNameX` + new `consumer/<type>` package + one line in `initQueue` + one `case` in `consumer_cmd.go`). `cliente_hub.acesso` (likely an auth token for the destination) is unused — no outbound auth/signing exists yet. INSERT/DELETE strategies (reuse `RowsStrategy` with their own stride) are still unimplemented, unrelated to this consumer work.
- **Related system, not yet reconciled**: `srp-hub-api` (sibling repo) already has a webhook-delivery route reading the *same* `clientes_hooks`/`cliente` tables — but triggered by an explicit internal API call from an ETL pipeline (`hub-events`) after it writes data, not by the DB write itself, so it misses any change that doesn't flow through that call (a gap this binlog-based system doesn't have). Before this consumer could replace that route: (1) **wire format differs** — `srp-hub-api` POSTs `{tipoModificacao, recurso}` bare; this consumer POSTs the full `queue.Event` envelope (`{id, tenant, table, action, timestamp, resource_id, payload: {tipoModificacao, recurso}}`) — a breaking change for any client receiver built against the old shape; (2) **resource coverage** — `srp-hub-api` also covers `clientes` (create/update/delete), this consumer only covers `pedidos`/`UPDATE` today.
